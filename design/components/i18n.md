# Internationalization

Only validation errors are ready to be translated. Everything else is
English for now.

| Messages | Who reads them | How they're made |
| --- | --- | --- |
| Validation errors | People using an application that validates their data | Plain data, without a message (`ruleId`, `instanceLocation`, `place`) |
| Schema problems | Schema authors, in the CLI and editors | English text in a `SchemaMessage`, from keywords' `check` and the resolver |
| Lint messages | Schema authors | English text from each rule's `file.message` |
| Thrown `Error`s | Developers calling the API | English text, for mistakes in the config or calls |

- A validation error is data, so it's translated outside this package.
  `@hyperjump/json-schema-errors` (`../json-schema-errors`) turns output
  into messages for people, and it localizes them with Fluent and
  `Intl.ListFormat`. `outputErrorMessage` is only a fallback in English
  that names the keyword and the instance location. Rejected: a message
  catalogue here, which would put a translation library in every bundle
  that validates (see [Small components](../principles/small-components.md)).
- Thrown `Error`s stay in English, like errors from Node.js. They're read
  by the developer who made the mistake, not shown to the people using
  what they built.
- Schema problems and lint messages are English text, with English
  grammar in them: `list` in `src/lint/list.js` ("'a', 'b', and 'c'") and
  verbs chosen by count. Translating them would take a stable id for each
  message, because a `ruleId` isn't unique (a rule can say different
  things), and its parameters as data, like keyword names, values, and
  counts. A translator outside this package could then render them, the
  way `json-schema-errors` renders validation errors, with
  `Intl.ListFormat` and `Intl.PluralRules` for lists and plurals. That
  changes every message, its test, and the rule pages that quote it, so
  it waits until a language other than English is needed.
- A locale is a value an operation or a renderer is given, not module
  state (see [No global state](../principles/no-global-state.md)).
  `json-schema-errors`' `addTranslation` adds to a catalogue in the
  module, which is the kind of global state v2 doesn't have. It's worth
  changing when it moves to v2.
